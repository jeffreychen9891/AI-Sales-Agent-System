# `infrastructure/observability/` —— 观测的声明式副本

**它解决的问题一句话**：dashboard 与 alert **只活在 Grafana 账号里**，
账号重建即无源可依（用户 2026-09-04 裁决三第一项；ADR-0101 §三.4；L2 原文）。

## 一、这份副本的权威性，说清楚

**今天的权威是 Grafana 账号，不是本目录。** 本目录是**重建来源**与**审阅对象**，
两件事都成立才有用，所以它必须诚实地说自己是怎么来的：

| 文件 | 它是怎么来的 | 因此可以拿它做什么 |
|---|---|---|
| `alerts/s06-stage-1m.yaml` | **誊抄**自 `evidence/m1a/s-06-observability-acceptance-2026-09-02.md` 的验收记录（含 rule id、folder、evaluation group、pending period、contact point 与三条表达式原文） | **可以拿它对账**；**不能拿它直接 provision**——它没有被从账号导出过，若有人在账号里改过，本文件就是旧的 |
| `alerts/m1b-planned.yaml` | **按 ADR-0101 §三.3 与 ADR-0103 §二.2 手写**的**计划态**。**2026-09-08 起十二条里有十条已经有源**（B0-4 装了采集器，B0-5 / B3-4b / B1-6 交付了指标），文件头逐条列了哪条有、哪条没有 | 可以拿它做 B0-7 建规则时的清单，**并且现在这份清单可以真的建了**——除了文件头标 ❌ 的两条 proactive（等 B4）；**规则本身仍未建，所以它描述的仍不是账号现状** |

**没有 `dashboards/`。** 今天仓里没有任何一份 dashboard 的定义，
**而我不知道账号里有哪些**——把一个猜出来的 dashboard 写进仓库，
比没有更糟（本仓已经为「一句不成立却好用的记录」付过账：还原点的 `ssh_scp`）。
**dashboard 的副本等一次真实导出**，登记在 §三。

## 二、怎么用

**重建账号时**：先按 `alerts/s06-stage-1m.yaml` 逐条比对**是否与你手上的账号一致**，
不一致以账号为准并**回写本文件**；然后再谈重建。

**建新规则时**（B0-7）：`alerts/m1b-planned.yaml` 是清单；建完之后
**从 Grafana 导出**并把导出的内容替换掉这里的手写版本，同时把本 README 的表格改掉。

## 三、这份副本今天缺的两半（不隐藏）

1. **没有从账号导出过**。三条现役规则是誊抄的，**誊抄与导出不是一回事**——
   到期条件：**下一次有人动 Grafana 规则时**，或 B0-7 建完那六条时，以先到者为准；
2. **没有 dashboard**。同上，等一次真实导出。

**这两条与 ADR-0101 §三.4 的要求的差距是明确的**：那条要求「保留声明式副本」，
本目录给出的是「一份可对账的记录 + 一份计划清单」，
**它让账号重建从「无源可依」变成「有源可校」，但还不是「一键重建」**。
